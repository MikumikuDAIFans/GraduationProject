## 二、逐章修改建议

### 第4章 相关技术介绍

#### 4.4.1 大语言模型集成技术 —— 必须修改（CRITICAL）

**问题**：论文声称系统使用"多模型混合路由架构"，将 Qwen 2.5 用于意图识别/规则任务，DeepSeek R1 用于复杂推理。这是**完全不准确的**。

**实际实现**：
- 系统**仅使用 Google Gemini 2.5 Flash** 一个模型
- 配置在 `.env` 中：`GEMINI_API_KEY` + `GEMINI_MODEL=models/gemini-2.5-flash`
- `GeminiClient`（`backend/app/tools/gemini.py`）是自定义异步 HTTP 客户端
- `LLM_PROVIDER=gemini`，虽然配置结构支持扩展，但实际上只接了 Gemini
- 没有任何 Qwen 或 DeepSeek 的依赖或调用代码

**修改建议**：
- 删除所有关于"多模型混合路由"、"Qwen 2.5"、"DeepSeek R1"的描述
- 改为准确描述：系统采用 Google Gemini 2.5 Flash 作为统一推理引擎
- 可以补充说明：架构设计上预留了 `LLM_PROVIDER` 配置项以支持未来扩展到其他模型
- 删除"意图识别与规则任务采用 Qwen 2.5，复杂推理与规划任务采用 DeepSeek R1"这段话

#### 4.4.2 多智能体通信与协调技术 —— 需要修正（HIGH）

**问题**：论文描述了 A2A 协议和标准化消息格式，暗示智能体之间有独立通信。实际实现是**顺序调用**。

**实际实现**：
- `SpecialistRegistry` + `AssistantConductor` 编排 6 个 specialist，**顺序执行**，非并行通信
- Specialist 之间通过可变的 `ConductorState` 对象传递状态，不是 A2A 消息协议
- 没有独立的智能体进程或消息队列通信

**修改建议**：
- 不要过度强调 A2A 协议的独立性
- 准确描述为："基于 Conductor 模式的顺序编排架构，各 Specialist 通过共享状态对象协作"
- 可以保留 A2A 作为理论背景，但要明确实际实现采用的是"中控编排 + 共享状态"模式

#### 4.4.3 检索增强生成（RAG）技术 —— 需要修正（MEDIUM）

**问题**：论文暗示 RAG 深度参与了核心推理流程。实际上 RAG 主要用于习惯/偏好检索辅助，核心推理仍走直接 Gemini 调用。

**实际实现**：
- ChromaDB 存储三个集合：`user_habits`、`event_experiences`、`user_preferences`
- 嵌入模型：Google `text-embedding-004`
- `EnhancedIntentParser` 结合规则解析与向量检索（如用户说"晚上回家做饭"时检索习惯数据建议时间）
- 但 Conductor proposal mode 下的 Understanding Specialist 主要依赖**正则规则 + Gemini LLM**，RAG 不是核心路径

**修改建议**：
- 准确描述 RAG 的定位：作为用户习惯和偏好的辅助检索层，增强上下文理解
- 不要把 RAG 描述成与 LLM 推理并列的核心能力
- 可以强调 RAG 在"长期记忆"中的作用（`assistant_memory` 运行时摘要注入上下文）
