## 第3页 · 研究背景

**标题：** 一、研究背景与意义

**内容：**
- 个人事务管理面临的问题：
  - 用户输入不规整（"明天下午去学校上课，记得提醒我早点出门"）
  - 一条需求涉及时间、地点、提醒、通勤等多个环节
  - 传统日历/备忘录需要用户手动拆分字段填表
- 大语言模型和智能体技术的发展，让"直接说话→系统理解→自动安排"成为可能
- 但现有方案还不够成熟：聊天结果不一定能变成可追踪的安排，状态流转、出错恢复、多端联动等问题关注不够

**讲稿：**
> 先说研究背景。日常生活中，个人事务管理不只是记一个会议时间，还涉及待办、通勤、提醒、临时改时间等各种情况。传统日历软件需要用户先把事情拆成标题、时间、地点再手动填表，但用户真实使用时脑子里想的往往不是这么规整的一张表。
>
> 这几年大语言模型技术发展比较快，让系统可以直接从自然语言里理解用户意图，再自动补全缺失信息。不过目前的方案还不够成熟，很多系统虽然有聊天入口，但聊天结果不一定能变成可以追踪、可以修改的安排。

## 第8页 · 多Agent协同模型

**标题：** 四、多Agent协同机制设计

**内容：**
- 核心思路：Conductor 中控编排 + 多 Specialist 顺序调度
- Agent 角色分工：

| 角色 | 职责 |
|------|------|
| Conductor | 统一调度，判断请求类型，决定调用顺序 |
| Understanding Specialist | 结构化理解，抽取时间、地点、目标等字段 |
| Task-or-Event Clarifier | 判断任务/日程类型，信息不足时生成补问 |
| Planning Specialist | 生成候选方案，按评分规则排序 |
| Proposal Manager | 持久化方案，管理状态流转 |
| Negotiation Specialist | 组织用户可读的确认文本 |
| Action Executor | 用户确认后执行实际写入 |

- 关键原则：模型生成内容 ≠ 系统执行结果，写入必须经过用户确认

**讲稿：**
> 多Agent协同是本系统的核心设计。整体思路是用 Conductor 作为中控编排者，顺序调度多个 Specialist。
>
> Conductor 负责判断当前输入是普通问答、创建请求还是待确认提案的后续回复，然后从 Specialist Registry 中选择需要参与的模块。Understanding Specialist 做结构化理解，Planning Specialist 生成候选方案，Proposal Manager 管理方案状态，Negotiation Specialist 组织确认文本，Action Executor 在用户确认后执行写入。
>
> 关键原则是：模型生成的内容不等于系统执行结果，真正的写入动作必须等用户确认以后才能执行。

## 第9页 · 自然语言理解

**标题：** 自然语言理解模型

**内容：**
- 结构化抽取对象：
  - request_type：请求类型（schedule_request / task_plan_request / query_request 等）
  - goal：用户真正想完成的目标
  - constraints：时间、地点、持续时长等限制条件
  - missing_fields：当前缺失的关键字段
  - ambiguities：可能造成误执行的模糊点
  - confidence：置信度，供 Conductor 判断是否进入澄清
- 理解策略：规则优先 + Gemini 兜底 + 保守合并
  - 常见日期词、动作词优先走规则
  - 规则置信度不足时调用 Gemini 按固定 schema 输出
  - 模型输出与规则冲突时取更保守的结果

**讲稿：**
> 自然语言理解部分，系统采用结构化抽取模型，把用户的一句话转成一个中间语义对象。这个对象包含请求类型、目标、约束条件、缺失字段、模糊点和置信度几个部分。
>
> 理解策略采用"规则优先、Gemini 兜底、保守合并"。常见的时间词、地点词和动作词优先由规则解析器处理，规则置信度不够时才调用 Gemini。当模型输出和规则输出冲突时，系统取更保守的结果，避免模型随意补全带来的风险。

## 第10页 · 任务/日程判定与补问

**标题：** 任务与日程类型判定

**内容：**
- 日程 vs 任务的区别：
  - 日程：有明确开始/结束时间（"明天下午三点上课"）
  - 任务：是一个目标，需要拆分（"这周把数据库复习完"）
- 判定依据：时间确定性、目标持续性、deadline 信息、用户纠正
- 信息不足时的处理：
  - 不强行猜测，生成补问
  - 例如："你是想把它作为待办任务保存，还是希望我直接帮你找几个复习时间块？"
  - 补问虽然增加一次交互，但能避免不确定事项错误落库

**讲稿：**
> 个人事务里最容易混淆的是任务和日程。日程有明确的开始和结束时间，比如"明天下午三点上课"；任务更像是一个目标，比如"这周把数据库复习完"。
>
> 系统通过时间确定性、目标持续性、deadline 信息和用户纠正来判断类型。如果无法判断，系统不会强行猜测，而是生成补问。比如"你是想把它作为待办任务保存，还是希望我直接帮你找几个复习时间块？"这一步虽然增加了一次交互，但能避免把不确定的事情错误地写入数据库。

## 第11页 · 候选方案评分

**标题：** 候选方案生成与评分算法

**内容：**
- Planning Specialist 先生成多个候选方案，再按可解释规则排序
- 评分公式：
  - Score = 0.30×时间匹配度 + 0.25×冲突安全度 + 0.15×截止时间紧迫度 + 0.15×通勤可行性 + 0.10×用户偏好匹配度 + 0.05×执行简洁度 - 风险惩罚
- 冲突检测：时间区间重叠判断 + buffer 扩展
- 出发时间估算：departure_time = event_start_time - travel_duration - safety_buffer
- 权重是原型阶段的经验设置，后续可根据用户习惯调整

**【配图：候选方案评分因子表】**

**讲稿：**
> Planning Specialist 的任务不是直接找一个看似合适的时间，而是先生成多个候选方案，再按可解释规则排序。
>
> 评分公式把候选方案拆成几个因子：时间匹配度、冲突安全度、截止时间紧迫度、通勤可行性、用户偏好匹配度和执行简洁度。每个因子归一化到 0 到 1 之间，再按权重加权求和。这样做的好处是排序过程能被解释、能调试，也便于后续根据用户习惯调整权重。
>
> 冲突检测采用时间区间重叠判断，还会把 buffer 和通勤时间一起扩展到事件占用区间。对于出行类事件，系统会估算出发时间，如果缓冲不足会在方案中说明风险。

## 第12页 · Proposal 协商状态机

**标题：** Proposal 协商状态机设计

**内容：**
- Proposal 是系统的核心对象：不是普通聊天消息，而是待决策计划单元
- 状态流转：pending → accepted → execution_pending → executed
- 协商流程：
  1. Conductor 识别请求 → 生成 proposal（pending）
  2. Negotiation Specialist 组织确认文本
  3. 用户回复"可以"/"改成4点"/"先不要安排"
  4. Conductor 判断是确认、修改还是拒绝
  5. 确认后 Action Executor 执行写入
- 幂等性：执行结果绑定 proposal，重复确认不重复写入

**【配图：Proposal 状态流转图】**

**讲稿：**
> Proposal 是本系统的中心对象。它不是普通聊天消息，而是系统围绕一个目标生成的待决策计划单元，里面包含背景、候选方案、风险说明、推荐方案和可执行动作。
>
> 协商流程是：Conductor 识别请求后生成 proposal，Proposal Manager 将其置为 pending，Negotiation Specialist 用自然语言说明方案和风险。用户确认后，Action Executor 才能执行写入。
>
> 这个设计的关键是幂等性：执行结果绑定 proposal 而不是绑定按钮点击。当一个 proposal 已经 executed 后，后续重复确认只返回第一次执行的回执，不会重复创建日程。

## 第13页 · 主动信号机制

**标题：** 主动信号与心跳机制

**内容：**
- 系统不只是被动等用户发消息，还能主动发现问题
- AssistantSignal 类型：
  - deadline_risk：高优先级任务临近 deadline
  - conflict_warning：日程时间冲突
  - departure_readiness：外出事件即将到达出发时间
  - daily_morning_review / daily_night_review：日常节律回顾
- 处理流程：Signal → Initiative Specialist 判断 → 是否转为 proposal → 用户确认
- 去重与冷却：dedup_key + cooldown 避免重复提醒
- 安全边界：可以发现风险、生成建议，但不能自动改日程

**讲稿：**
> 个人助理不应该只等用户发消息。本系统在被动 proposal 闭环之外，引入了 AssistantSignal 来描述系统主动发现的问题。
>
> 比如某个高优先任务临近 deadline 但还没有排程，就产生 deadline_risk signal；两个日程扩展缓冲后发生重叠，就产生 conflict_warning signal。Signal 被创建后，Initiative Specialist 判断是否需要转成 proposal，但不管哪种情况，最终都要等用户确认才能执行。
>
> 为了避免主动系统刷屏，signal 使用 dedup_key 和 cooldown 机制，同一个任务在冷却时间内不会重复提醒。

## 第14页 · 数据库设计

**标题：** 数据库设计

**内容：**
- 核心数据对象：
  - assistant_proposals：待确认方案（payload_json 保存 goal、context、options、execution）
  - assistant_signals：主动触发信号
  - assistant_thread_states：协商线程上下文
  - assistant_memory_update_candidates：待确认长期记忆候选
- 设计原则：
  - 业务写入资格由 proposal.status 决定
  - 主动触发原因由 signal 记录
  - 协商链路由 thread_state 保存
- 去重：dedup_key 在 service 层控制
- 过期：pending proposal 默认 24 小时过期

**【配图：新增智能体运行时数据对象表】**

**讲稿：**
> 数据库设计方面，系统在原有用户、事件、任务、提醒等基础表之上，新增了几个和智能体闭环直接相关的数据对象。
>
> assistant_proposals 是待确认方案的核心表，payload_json 保存目标、上下文、候选方案和执行结果。assistant_signals 保存主动触发信号，assistant_thread_states 保存协商线程上下文。
>
> 设计上有三个原则：业务写入资格由 proposal 状态决定，主动触发原因由 signal 记录，协商链路由 thread_state 保存。去重通过 dedup_key 在 service 层控制，过期机制防止用户确认过时的方案。

## 第15页 · 后端实现

**标题：** 后端架构实现

**内容：**
- 模块组织：
  - assistant_agents/ 目录承载智能体协同逻辑
  - assistant.py 作为 facade，根据模式选择 legacy/shadow/proposal
  - gemini.py 中的 GeminiClient 调用 Google Gemini 2.5 Flash
- Proposal API：
  - GET /api/assistant/proposals — 获取活跃提案
  - POST /proposals/{id}/confirm — 确认具体 option
  - reject / revise / retry / expire — 完整生命周期管理
- 运行模式：legacy（旧链路）/ shadow（新链路日志）/ proposal（确认后执行）
- Action Executor：只执行已确认的 actions，支持 create_event、create_task、create_task_with_events

**讲稿：**
> 后端实现方面，我在原有路由层和服务层的基础上，新增了 assistant_agents 目录来承载智能体协同逻辑。assistant.py 作为 facade，根据 ASSISTANT_CONDUCTOR_MODE 选择不同的运行模式。
>
> 围绕 proposal，后端提供了一组结构化 API，支持获取活跃提案、确认、拒绝、修改、重试和过期等完整生命周期操作。
>
> 系统保留了 legacy、shadow 和 proposal 三种运行模式。开发过程中我经常先用 shadow 模式观察新链路的表现，确认没问题了再切到 proposal 模式。这样新机制可以分阶段接入，不会一次性破坏原有系统。

## 第17页 · 典型协同过程示例

**标题：** 典型协同过程示例

**内容：**
- 用户输入："明天下午三点去学校上政治课，提醒我早点出门"
- 处理流程：
  1. Understanding Specialist → 抽取目标、日期、时间、地点、提醒需求
  2. Task-or-Event Clarifier → 判断为一次性日程
  3. Planning Specialist → 读取明天下午已有事件，估算通勤时间
  4. 生成方案A：15:00-16:00 上课，14:25 出发提醒
  5. 如有冲突 → 生成方案B：提示缓冲不足，建议提前或后移
  6. Proposal Manager → 包装成 pending proposal
  7. Negotiation Specialist → 返回确认文本
  8. 用户回复"可以" → Action Executor 创建事件和提醒

**【配图：协同流程示意图】**

**讲稿：**
> 下面用一个具体例子说明整个协同过程。
>
> 用户说"明天下午三点去学校上政治课，提醒我早点出门"。系统首先由 Understanding Specialist 抽取出目标、日期、时间、地点和提醒需求。Task-or-Event Clarifier 判断这是一次性日程。Planning Specialist 读取明天下午已有事件，估算从常用出发地到学校的通勤时间，生成方案A：15:00 到 16:00 上课，14:25 出发提醒。如果 14:25 附近有冲突，还会生成方案B，提示缓冲不足并建议调整。
>
> 用户回复"可以"后，Action Executor 创建事件和提醒。如果用户说"改成4点"，旧 proposal 进入 superseded，系统生成新 proposal，而不是直接覆盖执行。

## 第20页 · 结论与展望

**标题：** 六、结论与展望

**内容：**
- 完成工作：
  - 基于 Conductor 顺序编排的多Agent协同架构
  - Proposal-first + confirmation-before-write 核心机制

  - Action Executor 当前主要覆盖创建类动作
