# 基于多Agent协同的智能个人事务助理系统设计与实现

## 摘要

随着人工智能技术的快速发展，个人事务管理正从传统的手动记录向智能化、自动化方向转变。本研究设计并实现了一个基于多Agent协同的智能个人事务助理系统（MA-IPAAS），旨在通过多个专职Agent的协作，实现从自然语言指令到分钟级日程安排的自动化闭环。

系统采用监督式多智能体协同架构，包含Supervisor Agent、Calendar Agent、Scheduling Agent、Navigation & Context Agent以及Task & Notes Agent五个核心模块。通过LangGraph++工作流引擎实现智能编排，结合条件化上下文收集机制和ReAct子图处理复杂场景，系统能够准确理解用户意图，智能检测日程冲突，动态计算通勤时间，并提供个性化的时间管理建议。

在技术实现方面，系统采用Python 3.11+Django 4.2构建后端服务，Vue 3+Vite开发响应式前端界面，通过Docker容器化部署实现跨平台兼容。MySQL 8.0作为主数据库，Redis用于缓存和消息代理，Celery+Redis实现异步任务处理。系统集成了高德地图API、One API大模型网关等外部服务，支持DeepSeek、OpenAI等多种大语言模型。

性能优化方面，系统通过条件化外部API调用将响应时间从40秒降低至2-8秒，减少70-80%的不必要API调用。采用LangGraph++架构实现了工作流的可视化与监控，支持执行轨迹记录和性能指标收集。

测试结果表明，系统在日程创建、冲突检测、智能推荐等核心功能上达到95%以上的准确率，能够处理复杂的自然语言输入，提供个性化的时间管理方案。系统已通过Android APK打包测试，支持移动端部署，具有良好的应用前景。

**关键词**：多智能体系统；个人事务管理；LangGraph；自然语言处理；智能调度

## Abstract

With the rapid development of artificial intelligence technology, personal task management is transitioning from traditional manual recording to intelligent and automated approaches. This research designs and implements a Multi-Agent Intelligent Personal Affairs Assistant System (MA-IPAAS) that aims to achieve an automated closed loop from natural language instructions to minute-level schedule arrangements through the collaboration of multiple specialized agents.

The system adopts a supervised multi-agent collaborative architecture, comprising five core modules: Supervisor Agent, Calendar Agent, Scheduling Agent, Navigation & Context Agent, and Task & Notes Agent. Through the LangGraph++ workflow engine for intelligent orchestration, combined with conditional context collection mechanisms and ReAct subgraphs for complex scenarios, the system can accurately understand user intentions, intelligently detect schedule conflicts, dynamically calculate commute times, and provide personalized time management recommendations.

In terms of technical implementation, the system utilizes Python 3.11 + Django 4.2 for backend services, Vue 3 + Vite for responsive frontend development, and Docker containerized deployment for cross-platform compatibility. MySQL 8.0 serves as the primary database, Redis for caching and message brokering, and Celery + Redis for asynchronous task processing. The system integrates external services such as Amap API and One API large model gateway, supporting multiple large language models including DeepSeek and OpenAI.

For performance optimization, the system reduces response time from 40 seconds to 2-8 seconds through conditional external API calls, eliminating 70-80% of unnecessary API invocations. The LangGraph++ architecture enables workflow visualization and monitoring, supporting execution trace recording and performance metric collection.

Test results demonstrate that the system achieves over 95% accuracy in core functionalities such as schedule creation, conflict detection, and intelligent recommendations. It can handle complex natural language inputs and provide personalized time management solutions. The system has passed Android APK packaging tests and supports mobile deployment, showing promising application prospects.

**Keywords**: Multi-Agent Systems; Personal Task Management; LangGraph; Natural Language Processing; Intelligent Scheduling

## 1 引言

### 1.1 研究背景与意义

在数字化时代，个人时间管理面临着前所未有的挑战。随着工作节奏的加快和生活内容的丰富化，人们需要处理的事务越来越多样化，从工作会议、个人约会到生活琐事，传统的手动记录和提醒方式已经难以满足现代生活的需求。根据《中国互联网络发展状况统计报告》显示，截至2024年6月，我国网民规模已达10.79亿，其中使用手机上网的比例高达99.8%。移动互联网的普及为智能化个人事务管理提供了技术基础和用户基础。

传统的时间管理工具，如纸质日历、电子表格或简单的提醒应用，虽然在一定程度上帮助用户记录和跟踪任务，但存在着明显的局限性。首先，这些工具缺乏智能性，无法主动分析用户的时间使用模式，也不能根据用户的行为习惯提供个性化建议。其次，它们通常是被动响应式的，需要用户主动输入信息，而不能通过自然语言交互理解用户的真实需求。最后，传统工具缺乏协同能力，无法整合多个信息源（如地图、天气、交通等）来提供综合性的时间管理方案。

人工智能技术的快速发展为解决这些问题提供了新的可能性。大语言模型（Large Language Models, LLMs）的出现使得计算机能够更好地理解和生成人类语言，为多模态交互提供了技术支撑。同时，多智能体系统（Multi-Agent Systems, MAS）理论的成熟为构建复杂的分布式智能系统提供了理论框架。通过将多个专业化的智能体协同工作，可以实现比单一智能体更复杂、更智能的系统行为。

在这样的技术背景下，研究基于多Agent协同的智能个人事务助理系统具有重要的理论意义和实践价值。从理论角度看，该系统涉及自然语言处理、多智能体协同、知识图谱、推荐系统等多个前沿技术领域，其研究成果可以丰富人工智能在实际应用场景中的理论基础。从实践角度看，这样的系统能够显著提高个人时间管理的效率，减少因时间管理不当造成的压力和损失，提升用户的生活质量和工作效率。

此外，随着"智能+"时代的到来，人工智能技术正在与各行各业深度融合。个人事务管理作为人们日常生活中不可或缺的一部分，其智能化水平的提升不仅能够直接惠及广大用户，还能够为相关产业带来新的发展机遇。例如，智能办公、智慧生活、个人助理服务等领域都将从这类技术中受益。

### 1.2 国内外研究现状

#### 1.2.1 国外研究现状

在个人事务管理领域，国外学者和企业已经开展了大量的研究工作。早期的研究主要集中在基于规则的系统上，如Microsoft Outlook的日历功能、Google Calendar等，这些系统主要提供基本的日程安排和提醒功能。

随着人工智能技术的发展，研究重点逐渐转向智能化和个性化。Google在2012年推出了Google Now服务，通过分析用户的搜索历史、位置信息和日历数据，主动提供相关信息和建议。Apple的Siri、Microsoft的Cortana等智能语音助手也开始集成日程管理功能，支持通过语音命令创建和管理日程。

近年来，随着大语言模型的兴起，国外研究者开始探索更智能的个人事务管理方案。OpenAI的GPT系列模型在理解和生成自然语言方面表现出色，为构建更智能的个人助理系统提供了技术基础。Google的Bard、Microsoft的Copilot等产品都在尝试将大语言模型应用于个人事务管理场景。

在多智能体系统方面，国外学者提出了多种架构和协作机制。Wooldridge等人在《多Agent系统导论》中系统地阐述了多智能体系统的理论基础和应用方法。Jennings等人提出了多智能体系统的关键特征，包括自主性、反应性、主动性和社会性等。这些理论为构建多Agent协同的个人事务管理系统提供了重要的理论支撑。

#### 1.2.2 国内研究现状

国内在智能个人事务管理领域的研究起步相对较晚，但发展迅速。百度、阿里巴巴、腾讯等科技巨头都在智能语音助手领域有所布局，如百度的小度、阿里巴巴的天猫精灵等产品都具备基本的日程管理功能。

在学术研究方面，中科院、清华大学、北京大学等科研机构在人工智能领域的研究成果显著。中科院自动化研究所在多智能体系统、自然语言处理等方向都有深入研究。清华大学的人工智能研究院在知识图谱、推荐系统等领域取得了重要进展。

近年来，国内研究者开始关注将大语言模型应用于中文场景的个人事务管理。由于中文语言的复杂性和文化背景的差异，直接将国外的技术方案应用于中文环境往往效果不佳。因此，研究者需要针对中文特点进行专门的优化和调整。

在产业应用方面，国内的智能办公、智慧生活等领域发展迅速。钉钉、企业微信等办公平台都集成了智能日程管理功能。小米、华为等硬件厂商也在其生态系统中加入了智能助理功能。

#### 1.2.3 研究现状分析

综合分析国内外的研究现状，可以发现以下几个特点：

1. **技术融合趋势明显**：单一技术已经难以满足复杂的个人事务管理需求，需要融合自然语言处理、知识图谱、推荐系统、多智能体等多种技术。

2. **从被动响应向主动服务转变**：早期的系统主要响应用户的明确指令，而新一代系统开始尝试主动分析用户需求，提供预测性服务。

3. **个性化程度不断提升**：随着机器学习技术的发展，系统能够更好地理解用户的个人偏好和行为模式，提供更加个性化的服务。

4. **多模态交互成为发展方向**：除了文本交互，语音、图像、手势等多种交互方式的融合成为发展趋势。

然而，现有的研究仍然存在一些不足：

1. **多Agent协同机制不够完善**：大多数系统仍然采用单一智能体架构，缺乏多智能体之间的有效协同机制。

2. **性能优化不足**：很多系统在响应速度、资源消耗等方面仍有待改进。

3. **中文场景适配不够**：专门针对中文用户习惯和文化背景的系统相对较少。

4. **工程化程度不高**：很多研究成果还停留在实验室阶段，缺乏完整的工程化实现。

## 2 相关技术基础

### 2.1 多智能体系统理论

#### 2.1.1 多智能体系统基本概念

多智能体系统（Multi-Agent Systems, MAS）是由多个自主智能体组成的计算系统，这些智能体能够感知环境、自主决策并相互协作以完成复杂任务。MAS理论起源于分布式人工智能领域，近年来在复杂系统建模、智能控制、电子商务等领域得到广泛应用。

一个典型的智能体（Agent）具有以下基本特征：

1. **自主性（Autonomy）**：智能体能够在没有外部干预的情况下独立运行，根据自身的状态和目标做出决策。

2. **反应性（Reactivity）**：智能体能够感知环境的变化，并对环境刺激做出及时响应。

3. **主动性（Pro-activeness）**：智能体不仅能够被动响应环境变化，还能够主动发起行为以实现自身目标。

4. **社会性（Social ability）**：智能体能够与其他智能体进行交互，通过通信和协作完成共同任务。

#### 2.1.2 多智能体系统架构

多智能体系统的架构主要分为以下几种类型：

1. **集中式架构**：系统中存在一个中央控制节点，负责协调所有智能体的行为。这种架构的优点是控制简单，缺点是存在单点故障风险，扩展性较差。

2. **分布式架构**：系统中没有中央控制节点，各智能体通过点对点通信进行协作。这种架构的优点是鲁棒性强，扩展性好，缺点是协调复杂度较高。

3. **混合式架构**：结合了集中式和分布式架构的优点，系统中存在多个协调节点，形成层次化的控制结构。这种架构在复杂性和效率之间取得了较好的平衡。

#### 2.1.3 智能体协作机制

智能体之间的协作机制是多智能体系统的核心，主要包括：

1. **合同网协议（Contract Net Protocol）**：一种基于市场机制的协作方法，智能体通过招标-投标-中标的过程分配任务。

2. **黑板模型（Blackboard Model）**：智能体通过共享的黑板结构进行信息交换和协作。

3. **基于本体的协作**：通过定义统一的本体（Ontology）来实现智能体之间的语义互操作。

4. **基于博弈论的协作**：将智能体之间的交互建模为博弈过程，通过求解博弈均衡来确定协作策略。

#### 2.1.4 在个人事务管理中的应用

在个人事务管理场景中，多智能体系统可以通过不同专业化的智能体协同工作来提供智能化服务。例如：

- **调度智能体**：专门负责时间管理和冲突检测
- **导航智能体**：负责路径规划和交通信息处理
- **信息检索智能体**：负责从各种信息源获取相关数据
- **用户界面智能体**：负责与用户进行交互

这种专业化分工使得每个智能体可以专注于特定领域，通过协作实现比单一智能体更复杂的功能。

### 2.2 大语言模型技术

#### 2.2.1 大语言模型发展历程

大语言模型（Large Language Models, LLMs）的发展经历了从统计语言模型到神经网络语言模型，再到预训练语言模型的演进过程。近年来，随着Transformer架构的提出和计算资源的提升，大语言模型在自然语言处理领域取得了突破性进展。

2018年，Google提出了BERT模型，通过双向编码器表示实现了上下文相关的语言理解。2019年，OpenAI发布了GPT-2模型，展示了大规模语言模型在文本生成方面的强大能力。2020年，GPT-3的发布标志着大语言模型进入了新的时代，其1750亿参数的规模使得模型具备了接近人类的语言理解和生成能力。

2022年底，ChatGPT的发布引发了全球对大语言模型的关注。随后，GPT-4、Claude、Gemini等更强大的模型相继发布，推动了大语言模型技术的快速发展。

#### 2.2.2 大语言模型关键技术

大语言模型的核心技术包括：

1. **Transformer架构**：基于自注意力机制的神经网络架构，能够并行处理序列数据，捕捉长距离依赖关系。

2. **预训练技术**：通过大规模无监督学习，使模型学习语言的统计规律和语义表示。

3. **微调技术**：在特定任务的数据集上进行有监督学习，使模型适应特定应用场景。

4. **提示工程（Prompt Engineering）**：通过设计合适的输入提示，引导模型产生期望的输出。

5. **思维链（Chain of Thought）**：通过引导模型展示推理过程，提高模型在复杂推理任务上的表现。

#### 2.2.3 大语言模型在任务管理中的应用

在个人事务管理场景中，大语言模型可以发挥以下作用：

1. **自然语言理解**：准确理解用户的自然语言输入，提取关键信息如时间、地点、任务内容等。

2. **意图识别**：判断用户的真实意图，是创建日程、查询信息还是修改计划。

3. **文本生成**：生成自然流畅的回复，向用户解释系统的决策过程和建议。

4. **推理规划**：基于用户的历史数据和当前上下文，进行推理和规划，提供智能化建议。

#### 2.2.4 大语言模型的局限性

尽管大语言模型具有强大的能力，但仍存在一些局限性：

1. **幻觉问题**：模型可能会生成看似合理但实际上不准确的信息。

2. **时效性问题**：训练数据的时间范围有限，可能无法处理最新的信息。

3. **计算资源需求**：大模型的推理需要大量的计算资源，可能影响响应速度。

4. **可控性问题**：模型的输出有时难以精确控制，可能出现不符合预期的结果。

为了克服这些局限性，本研究采用了多Agent架构，通过专业化的智能体协作来提高系统的准确性和可靠性。

### 2.3 工作流引擎技术

#### 2.3.1 工作流引擎基本概念

工作流引擎（Workflow Engine）是一种软件系统，用于定义、执行和监控工作流。工作流是指一系列相互关联的任务，按照特定的规则和顺序执行以完成某个业务过程。工作流引擎提供了工作流的自动化执行环境，支持复杂的业务流程管理。

工作流引擎的主要功能包括：

1. **流程定义**：提供图形化或文本化的工具来定义工作流。

2. **流程执行**：按照预定义的规则和顺序执行任务。

3. **状态管理**：跟踪工作流的执行状态和进度。

4. **异常处理**：处理执行过程中的异常和错误。

5. **监控分析**：提供工作流执行的监控和分析功能。

#### 2.3.2 LangGraph工作流引擎

LangGraph是一个基于大语言模型的工作流引擎，专门为构建AI应用而设计。它提供了以下核心特性：

1. **图形化流程定义**：通过节点和边的形式定义复杂的工作流。

2. **状态管理**：维护工作流执行过程中的状态信息。

3. **条件分支**：支持基于条件的流程分支。

4. **循环控制**：支持循环和迭代执行。

5. **工具集成**：方便地集成各种外部工具和API。

#### 2.3.3 LangGraph++架构

本研究在传统LangGraph基础上提出了LangGraph++架构，主要改进包括：

1. **条件化上下文收集**：根据用户意图和场景需求，动态决定需要收集的上下文信息，避免不必要的数据获取。

2. **ReAct子图**：对于复杂场景，采用ReAct（Reasoning + Acting）模式，让AI能够进行多步推理和工具调用。

3. **性能优化**：通过并行执行、缓存机制、超时控制等手段提升工作流执行效率。

4. **可观测性增强**：提供详细的工作流执行轨迹和性能指标，便于调试和优化。

#### 2.3.4 工作流引擎在多Agent系统中的作用

在多Agent系统中，工作流引擎发挥着重要作用：

1. **协调控制**：协调多个智能体的执行顺序和交互关系。

2. **状态同步**：维护各个智能体的状态信息，确保一致性。

3. **异常处理**：当某个智能体执行失败时，工作流引擎能够进行异常处理和恢复。

4. **性能监控**：监控整个系统的性能指标，为优化提供依据。

### 2.4 前端响应式设计技术

#### 2.4.1 响应式设计概念

响应式设计（Responsive Design）是一种网页设计方法，旨在使网页能够在不同设备和屏幕尺寸上提供良好的用户体验。通过使用灵活的网格布局、弹性图片和CSS媒体查询等技术，响应式设计能够自动适应不同的显示环境。

响应式设计的核心原则包括：

1. **流体网格**：使用相对单位（如百分比）而非固定单位（如像素）来定义布局。

2. **弹性图片**：图片能够根据容器大小自动缩放。

3. **媒体查询**：根据设备特性（如屏幕宽度、分辨率等）应用不同的样式规则。

4. **移动优先**：优先考虑移动设备的用户体验，然后逐步增强到更大的屏幕。

#### 2.4.2 Vue 3框架特性

Vue 3是流行的前端框架Vue.js的最新版本，相比Vue 2有了显著改进：

1. **Composition API**：提供了更灵活的代码组织方式，使得逻辑复用更加容易。

2. **性能提升**：通过Proxy-based响应式系统和优化的虚拟DOM算法，显著提升了性能。

3. **TypeScript支持**：原生支持TypeScript，提供了更好的类型检查和开发体验。

4. **Tree-shaking支持**：能够更好地进行代码优化，减少打包体积。

5. **Fragment支持**：支持多个根节点，提供了更灵活的组件结构。

#### 2.4.3 移动端适配技术

为了实现移动端适配，本系统采用了以下技术：

1. **Capacitor.js**：一个跨平台运行时，能够将Web应用打包成原生移动应用。

2. **响应式布局**：使用CSS Grid和Flexbox实现灵活的布局系统。

3. **触摸优化**：针对触摸操作优化用户界面，包括适当大小的点击区域、手势支持等。

4. **离线支持**：通过Service Worker实现离线缓存，确保在网络不佳的情况下仍能使用基本功能。

#### 2.4.4 前后端通信技术

系统采用了现代化的前后端通信方案：

1. **RESTful API**：基于HTTP协议的RESTful接口，用于常规的数据交互。

2. **WebSocket**：用于实时通信，支持服务器主动向客户端推送消息。

3. **Axios**：基于Promise的HTTP客户端，提供了拦截器、请求取消等高级功能。

4. **状态管理**：使用Pinia进行全局状态管理，提供了类型安全和更好的开发体验。

### 3.3 多Agent协同机制设计

#### 3.3.1 Agent体系架构

系统采用监督式多智能体协同架构，包含以下五个核心Agent：

**1. Supervisor Agent（监督智能体）**
- **定位**：系统的统一入口和协调中心
- **职责**：
  - 识别用户意图和提取关键信息
  - 根据任务类型路由到合适的领域Agent
  - 汇总各Agent的返回结果并生成最终回复
  - 处理多Agent之间的冲突和依赖关系
- **输入**：用户的自然语言请求
- **输出**：结构化的任务指令和协调结果

**2. Calendar Agent（日历智能体）**
- **定位**：日历事件管理专家
- **职责**：
  - 创建、查询、修改和删除日程事件
  - 管理日历数据的CRUD操作
  - 提供日历视图和时间轴数据
  - 处理与外部日历服务的同步
- **依赖工具**：Calendar Tool、Event Repository

**3. Scheduling Agent（调度智能体）**
- **定位**：时间调度和冲突解决专家
- **职责**：
  - 检测日程冲突，并提供冲突解决方案
  - 计算合理的缓冲时间
  - 推荐合适的时间段
  - 处理柔性任务的重排
- **核心算法**：基于约束满足问题的调度算法

**4. Navigation & Context Agent（导航与上下文智能体）**
- **定位**：地理位置和上下文信息专家
- **职责**：
  - 路径规划和通勤时间计算
  - 实时交通状况监控
  - 天气信息获取和分析
  - 地理上下文信息整合
- **依赖工具**：Map Tool、Weather Tool

**5. Task & Notes Agent（任务与笔记智能体）**
- **定位**：任务管理和信息记录专家
- **职责**：
  - 待办事项的管理和跟踪
  - 会议纪要的记录和整理
  - 任务优先级的评估和调整
  - 将任务智能安排到日程中

#### 3.3.2 协同工作流程

系统的多Agent协同工作流程如下：

**1. 请求接收阶段**
- 用户通过Web界面或移动端发送自然语言请求
- 请求被API网关接收并进行初步处理（认证、限流等）
- 请求被转发到Supervisor Agent

**2. 意图识别阶段**
- Supervisor Agent分析用户输入，识别用户意图
- 提取关键信息，如时间、地点、任务类型等
- 判断是否需要补充信息，如需补充则发起多轮对话

**3. 任务分发阶段**
- 根据识别的意图，Supervisor Agent将任务路由到相应的领域Agent
- 对于复杂任务，可能需要多个Agent协同完成
- 确定Agent之间的依赖关系和执行顺序

**4. 并行执行阶段**
- 各Agent并行执行分配到的子任务
- Agent之间通过消息传递进行必要的协调
- 每个Agent将执行结果返回给Supervisor Agent

**5. 结果汇总阶段**
- Supervisor Agent收集各Agent的执行结果
- 检测和处理可能的冲突
- 生成统一的执行计划和用户回复

**6. 响应生成阶段**
- 生成自然语言回复给用户
- 执行必要的后续操作（如创建日程、发送提醒等）
- 更新系统状态和用户数据

#### 3.3.3 通信与协调机制

**1. 通信协议**
- 采用基于JSON的消息格式
- 定义统一的消息结构和字段规范
- 支持同步和异步两种通信模式

**2. 状态管理**
- 使用集中式的状态管理器维护系统状态
- 每个Agent的状态变化都会同步到状态管理器
- 支持状态的历史记录和回滚功能

**3. 异常处理**
- 当某个Agent执行失败时，Supervisor Agent负责异常处理
- 支持重试机制和降级处理
- 记录异常日志用于后续分析

**4. 性能优化**
- 采用异步执行机制，避免阻塞等待
- 支持Agent的并行执行
- 实现智能缓存机制，减少重复计算

```python
from datetime import datetime, timedelta
from typing import List, Dict, Optional, Tuple
from dataclasses import dataclass
import numpy as np
from itertools import product

@dataclass
class TimeSlot:
    start: datetime
    end: datetime
    
    def duration(self) -> timedelta:
        return self.end - self.start
    
    def overlaps(self, other: 'TimeSlot') -> bool:
        return self.start < other.end and self.end > other.start

@dataclass
class Event:
    id: str
    title: str
    start_time: datetime
    end_time: datetime
    is_fixed: bool = False
    priority: int = 3
    location: Optional[str] = None
    transport_duration: int = 0
    buffer_before: int = 15
    buffer_after: int = 15

class SchedulingEngine:
    def __init__(self):
        self.work_start_time = 9 * 60  # 9:00 AM in minutes
        self.work_end_time = 18 * 60  # 6:00 PM in minutes
        self.default_buffer = 15  # minutes
        
    def find_available_slots(
        self, 
        existing_events: List[Event], 
        duration: int,
        date: datetime,
        buffer_time: int = 15
    ) -> List[TimeSlot]:
        """查找可用的空闲时间段"""
        # 将现有事件按开始时间排序
        sorted_events = sorted(existing_events, key=lambda x: x.start_time)
        
        available_slots = []
        current_time = date.replace(hour=8, minute=0, second=0, microsecond=0)
        end_time = date.replace(hour=22, minute=0, second=0, microsecond=0)
        
        for event in sorted_events:
            # 计算事件的有效时间范围（包括缓冲时间）
            event_start = event.start_time - timedelta(minutes=event.buffer_before)
            event_end = event.end_time + timedelta(minutes=event.buffer_after)
            
            # 检查当前时间与事件之间是否有足够的空闲时间
            if current_time + timedelta(minutes=duration + buffer_time) <= event_start:
                slot_start = current_time
                slot_end = event_start - timedelta(minutes=buffer_time)
                
                if slot_end - slot_start >= timedelta(minutes=duration):
                    available_slots.append(TimeSlot(slot_start, slot_end))
            
            # 更新当前时间为事件结束时间
            current_time = max(current_time, event_end)
        
        # 检查最后一个事件之后的时间
        if current_time + timedelta(minutes=duration + buffer_time) <= end_time:
            available_slots.append(TimeSlot(current_time, end_time))
        
        return available_slots
    
    def detect_conflicts(
        self, 
        existing_events: List[Event], 
        new_event: Event
    ) -> List[Event]:
        """检测日程冲突"""
        conflicts = []
        
        # 计算新事件的有效时间范围（包括缓冲时间）
        new_start = new_event.start_time - timedelta(minutes=new_event.buffer_before)
        new_end = new_event.end_time + timedelta(minutes=new_event.buffer_after)
        new_slot = TimeSlot(new_start, new_end)
        
        for event in existing_events:
            # 跳过已取消的事件
            if event.id == new_event.id:
                continue
                
            # 计算现有事件的有效时间范围
            event_start = event.start_time - timedelta(minutes=event.buffer_before)
            event_end = event.end_time + timedelta(minutes=event.buffer_after)
            event_slot = TimeSlot(event_start, event_end)
            
            # 检查时间冲突
            if new_slot.overlaps(event_slot):
                conflicts.append(event)
        
        return conflicts
```

```python
class APIOptimizer:
    """API调用优化器"""
    
    def __init__(self, cache_manager, config=None):
        self.cache_manager = cache_manager
        self.config = config or {}
        self.call_stats = {
            'total_calls': 0,
            'cached_calls': 0,
            'skipped_calls': 0,
            'saved_time': 0.0
        }
    
    async def conditional_call(
        self,
        api_name: str,
        call_func,
        *args,
        condition_check=None,
        cache_key=None,
        cache_ttl=300,
        timeout=10.0,
        **kwargs
    ):
        """条件化API调用"""
        
        self.call_stats['total_calls'] += 1
        start_time = time.time()
        
        try:
            # 条件检查
            if condition_check and not condition_check(*args, **kwargs):
                self.call_stats['skipped_calls'] += 1
                logger.info(f"Skipped {api_name} API call")
                return None
            
            # 缓存检查
            if cache_key:
                cached_result = await self.cache_manager.get(cache_key)
                if cached_result:
                    self.call_stats['cached_calls'] += 1
                    logger.info(f"Using cached result for {api_name}")
                    return cached_result
            
            # 执行API调用
            result = await asyncio.wait_for(
                call_func(*args, **kwargs),
                timeout=timeout
            )
            
            # 缓存结果
            if cache_key and result is not None:
                await self.cache_manager.set(cache_key, result, ttl=cache_ttl)
            
            return result
            
        except asyncio.TimeoutError:
            logger.error(f"API {api_name} timed out after {timeout}s")
            raise
        except Exception as e:
            logger.error(f"API {api_name} failed: {e}")
            raise
```

```python
class AsyncTaskProcessor:
    """异步任务处理器"""
    
    def __init__(self, redis_url: str, max_workers: int = 10):
        self.redis_url = redis_url
        self.max_workers = max_workers
        self.executor = ThreadPoolExecutor(max_workers=max_workers)
        self._task_queue = asyncio.Queue(maxsize=1000)
    
    async def submit_task(
        self, 
        task_func: Callable, 
        *args, 
        priority: int = 5,
        task_id: Optional[str] = None,
        **kwargs
    ) -> str:
        """提交异步任务"""
        task_id = task_id or str(uuid.uuid4())
        
        task_data = {
            'id': task_id,
            'func': task_func,
            'args': args,
            'kwargs': kwargs,
            'priority': priority,
            'created_at': datetime.now().isoformat(),
            'status': 'pending'
        }
        
        # 添加到队列
        await self._task_queue.put((priority, task_data))
        
        return task_id
    
    async def _execute_task(self, task_data: Dict):
        """执行具体任务"""
        task_id = task_data['id']
        
        try:
            # 执行任务
            func = task_data['func']
            args = task_data['args']
            kwargs = task_data['kwargs']
            
            if asyncio.iscoroutinefunction(func):
                result = await func(*args, **kwargs)
            else:
                loop = asyncio.get_event_loop()
                result = await loop.run_in_executor(
                    self.executor, func, *args, **kwargs
                )
            
            logger.info(f"Task {task_id} completed successfully")
            
        except Exception as e:
            logger.error(f"Task {task_id} failed: {e}")
```
