# 个人事务助手可落地简化方案

## 1. 核心目标

本方案不继承之前的 Agent 命名和架构设定，而是基于已收集的 8 个开源仓库的常见实现方式，重新收敛出一版更简单、可落地、适合毕业设计实现的个人事务助手系统。

系统核心理念只有一条：

**AI 不只是被动响应，而是能围绕“个人时间安排”在合适的时机主动提醒、主动建议、主动处理冲突。**

因此，本系统必须稳定覆盖以下能力：

1. 日程规划
2. 日程建议
3. 日程冲突处理
4. 与行动相关的提醒
5. 在合适时间主动触发建议或提醒

## 2. 从参考仓库中提炼出的实现共识

结合 [reference](/E:/GraduationProject/reference) 下的 8 个项目，可以提炼出几个最适合毕业设计的共同模式：

1. 不要先做复杂多 Agent 平台，先做一个清晰的主工作流。
2. 日历、任务、提醒、通勤、天气等能力要工具化，不要混进提示词。
3. 系统必须有显式状态，而不是单靠对话历史。
4. 主动提醒能力本质上不是聊天能力，而是“触发器 + 规则 + 调度器”。
5. 用户交互最好同时包含“日历视图”和“助手视图”。

所以，这一版方案不先定义具体有几个 Agent，而是先定义一个更稳定的系统骨架。

## 3. 推荐的最简系统骨架

建议把整个系统收敛成 4 个核心模块：

1. **Assistant Core**
2. **Schedule Engine**
3. **Tool Layer**
4. **Trigger & Reminder Engine**

这 4 个模块就足够支撑毕业设计的核心价值。

## 3.1 Assistant Core

这是系统的统一入口，负责接收用户消息、理解意图、组织调用流程、返回结果。

它负责：

1. 解析用户输入
2. 抽取时间、地点、任务类型等关键信息
3. 决定是查询、创建、修改、建议还是提醒处理
4. 调用 Schedule Engine 和 Tool Layer
5. 生成自然语言回复

它不负责：

1. 直接访问地图 API
2. 直接写复杂排程逻辑
3. 直接承担定时触发任务

这部分的设计参考了：

1. [reference/todo-work-agent](/E:/GraduationProject/reference/todo-work-agent)
2. [reference/calendar-ai](/E:/GraduationProject/reference/calendar-ai)

## 3.2 Schedule Engine

这是整个毕业设计的业务核心，也是和普通聊天机器人拉开差距的关键。

它负责：

1. 日程冲突检测
2. 合理时间段推荐
3. 通勤前置时间计算
4. 柔性任务插入空档
5. 延误后的重排建议

建议不要把它做成“大模型随便发挥”的黑盒，而要做成：

**规则优先 + AI 辅助解释/建议**

也就是说：

1. 冲突检测用规则
2. 空闲时段计算用规则
3. 缓冲时间计算用规则
4. AI 主要负责理解需求和把结果表达成人话

这样更稳，也更适合毕业设计答辩。

## 3.3 Tool Layer

这个模块专门封装所有外部能力。

建议至少包含：

1. `Calendar Tool`
2. `Task Tool`
3. `Map Tool`
4. `Weather Tool`
5. `Notification Tool`

### Calendar Tool

提供：

1. 创建日程
2. 查询日程
3. 修改日程
4. 删除日程
5. 查询空闲时间

这部分非常适合参考 [reference/calendar-mcp](/E:/GraduationProject/reference/calendar-mcp) 的工具化思路。

### Task Tool

提供：

1. 创建待办
2. 查询待办
3. 更新状态
4. 估算时长
5. 获取未完成任务列表

### Map Tool

提供：

1. 估算地点间通勤时长
2. 计算建议出发时间
3. 支持交通方式差异

### Notification Tool

提供：

1. 定时提醒
2. 冲突提醒
3. 出发提醒
4. 日程变更提醒
5. 建议提醒

## 3.4 Trigger & Reminder Engine

这是这次方案里最重要的新增重点。

你毕业设计真正有价值的点，不只是“我问一句，你答一句”，而是：

**系统能在合适时机主动做事。**

所以必须单独有一个触发与提醒引擎。

它负责：

1. 定时扫描未来一段时间内的事件
2. 找出需要提醒的事项
3. 找出存在冲突或风险的事项
4. 发现空档后推送建议
5. 在天气、路况、延误变化时触发重规划

它的本质不是 Agent，而是一个后台调度机制。

实现上建议用：

1. `Celery Beat + Celery Worker`
2. 或最简化的定时任务模块

## 4. 系统最小工作流

## 4.1 用户主动创建日程

流程：

1. 用户输入一句自然语言
2. Assistant Core 提取时间、地点、类型
3. Schedule Engine 检查冲突和建议时段
4. 必要时调用 Map Tool 计算通勤与出发时间
5. Calendar Tool 写入事件
6. Notification Tool 注册提醒任务
7. 前端返回创建结果和建议说明

## 4.2 用户请求“帮我安排今天/明天”

流程：

1. Assistant Core 获取今天或明天已有事件
2. Task Tool 获取未完成待办
3. Schedule Engine 识别空闲时段
4. 根据任务时长、优先级、截止时间生成建议安排
5. 用户确认后写入日程或待办计划

## 4.3 系统主动提醒

流程：

1. Trigger Engine 定时扫描近期事件
2. 判断是否接近提醒窗口
3. 如果需要提前出发，则调用 Map Tool 重新计算
4. 如果发现时间风险或冲突，则触发重新建议
5. Notification Tool 向前端或消息渠道推送提醒

## 4.4 系统主动建议

流程：

1. Trigger Engine 检查当日空档
2. 检查待办池里是否有合适任务
3. 判断是否存在截止日期风险
4. 如果存在合适建议，则推送：
   - 现在有 40 分钟空档，建议处理 XX
   - 你 18:00 有外出安排，建议 17:20 准备出发

这部分正是你毕业设计最有辨识度的地方。

## 5. 为什么这版方案更适合毕业设计

相比复杂多 Agent 平台，这一版更适合毕业设计，原因有五点：

1. 结构简单，开发边界清晰
2. 主功能集中，容易做出演示效果
3. 主动提醒的亮点更突出
4. 能解释为“AI 辅助调度系统”，而不是泛化聊天机器人
5. 后续如果需要，再往多 Agent 演进也很自然

## 6. 推荐的数据模型

最少只保留 5 张核心表即可：

1. `users`
2. `events`
3. `tasks`
4. `reminders`
5. `schedule_logs`

## 6.1 events

建议字段：

1. `id`
2. `title`
3. `start_time`
4. `end_time`
5. `location_name`
6. `location_coords`
7. `event_type`
8. `is_fixed`
9. `buffer_before`
10. `buffer_after`
11. `travel_mode`
12. `travel_duration`
13. `status`

## 6.2 tasks

建议字段：

1. `id`
2. `content`
3. `estimated_duration`
4. `priority`
5. `deadline`
6. `status`
7. `can_split`
8. `preferred_period`

## 6.3 reminders

建议字段：

1. `id`
2. `target_type`
3. `target_id`
4. `remind_at`
5. `remind_type`
6. `status`
7. `message`

### 解释

这张表非常关键，因为它决定系统是否真的具备“主动提醒”能力。

## 7. 推荐技术选型

基于你当前项目背景，推荐保留这套更稳妥的技术组合：

### 后端

1. `Python 3.11`
2. `Django + DRF`
3. `Celery + Redis`
4. `MySQL`
5. `Channels` 或简化版实时推送

### AI 工作流

1. 初期不强绑定复杂多 Agent 框架
2. 用一个主 Assistant 工作流 + 工具调用先跑通
3. 后续如果需要，再演进到 Supervisor + 多角色分工

### 前端

1. `Vue 3 + Vite`
2. 一个日历页
3. 一个助手页
4. 一个提醒/建议展示区

## 8. 推荐的前端形态

前端不要做成纯聊天机器人界面，建议用三块区域：

1. **日历区**
   - 今天、明天、本周日程
   - 冲突高亮
   - 建议插入时段可视化

2. **助手区**
   - 自然语言输入
   - 创建、修改、查询日程
   - 接收解释和建议

3. **提醒区**
   - 即将开始事项
   - 出发提醒
   - 推荐安排
   - 风险提示

这部分可以参考 [reference/calendar-ai](/E:/GraduationProject/reference/calendar-ai) 的“calendar + assistant”组合思路，但要进一步加强主动提醒展示。

## 9. 最推荐的实现优先级

如果你要真正做出来，我建议按下面顺序推进：

## 第一阶段：最小闭环

目标：

1. 自然语言创建日程
2. 查询当天日程
3. 基础冲突检测
4. 基础提醒

## 第二阶段：核心亮点

目标：

1. 自动建议空闲时间安排
2. 出发提醒
3. 冲突处理建议
4. 柔性任务插入空档

## 第三阶段：展示增强

目标：

1. 页面可视化更完整
2. 系统日志可展示
3. 主动提醒过程可演示
4. 支持简单移动端适配

## 10. 这一版方案的最终定义

最终建议把你的毕业设计定义为：

**一个面向个人时间管理的智能事务助手系统。系统以日程、待办和提醒为核心对象，通过自然语言交互、规则驱动排程和 AI 辅助建议，实现对用户日常行动的主动提醒、冲突处理与合理安排。**

这一定义的优点是：

1. 不被具体 Agent 数量绑定
2. 重点突出“个人事务”和“主动提醒”
3. 容易落到代码和演示
4. 后续仍可以自然扩展为多 Agent 版本

## 11. 当前最建议你坚持的产品重点

如果只保留一句产品原则，我建议就是这句：

**系统要像一个会看时间、会看空档、会提醒、会建议的个人事务助手，而不是一个只会聊天的 AI。**
