# AI 助手浏览器级全场景测试问题与预期结果 V1

> 文档状态：drafting  
> 依据文档：`docs/development/AI_ASSISTANT_REDESIGN_PLAN_V1.md`  
> 测试层级：浏览器级验收 / 端到端行为验收  
> 适用范围：AI 助手面板、纯文本交互、Proposal 闭环、主动跟进、记忆候选、出发提醒、幂等与异常路径  
> 最后更新：2026-05-12

---

## 一、测试目标

本测试文档用于补齐当前实际测试覆盖不足的问题，重点验证 AI 助手是否真正达到重设计方案要求的产品行为：

1. 用户在浏览器中输入自然语言后，系统应表现出“先理解 -> 再建议 -> 再确认 -> 再执行”的链路。
2. 所有会写入任务、日程、状态、长期记忆的操作，必须先生成可确认的 proposal 或记忆候选，不允许直接落库。
3. 当前对话区、待确认事项区、主动跟进区应能让用户看清系统正在提案、总结、提醒还是澄清。
4. 多个 pending proposal 并存时，纯文本确认必须可唯一指代；无法唯一指代时必须澄清。
5. 主动触发、出发提醒、晨间汇报、睡前复盘必须具备来源、理由、回复方式和去重约束。
6. 浏览器端可观察到稳定的状态变化，不出现旧 workflow、弱规则分句、重复执行和静默失败。
7. 多轮对话中，系统必须保留并复用当前线程内已经确认或已提出的槽位信息，不得在用户补充信息后丢失标题、地点、时间、proposal 目标或修正意图。

## 二、测试环境与准备

### 2.1 基础环境

- 前端：启动本地 Web 应用，并通过浏览器访问助手页面。
- 后端：启动 API 服务、数据库迁移完成、WebSocket 可连接。
- AI Provider：主模型可调用；若配置了 fallback，应能在主模型失败时降级。
- 测试账号：使用独立测试用户或测试数据库，避免污染真实数据。
- 浏览器：至少覆盖 Chromium 桌面端；关键响应式用例补测移动视口。

### 2.2 浏览器检查口径

每条用例至少检查以下证据：

- 当前对话区是否展示正确回复。
- 当前待确认事项区是否展示 pending proposal 的短标识、摘要和状态。
- 主动跟进区是否展示晨间、睡前、出发、风险等主动消息。
- 日程 / 任务页面刷新后是否与执行结果一致。
- 重复刷新页面后，pending / executed / rejected 状态是否保留。
- 网络面板中对应接口无 4xx / 5xx；WebSocket 事件能推动 UI 更新。
- 对多轮用例，必须记录每一轮输入、助手回复、pending proposal 状态变化、业务表是否落库。
- 对异常用例，必须记录错误提示是否可理解、输入框是否恢复、是否出现重复提交或重复执行。

### 2.3 全局通过标准

以下断言适用于所有写操作场景：

- 未确认前不得创建、修改、删除、完成任何 event / task。
- 未确认前不得写入长期 `.md` 记忆文件。
- proposal 必须先进入 `pending`，确认后进入 `accepted` 或 `execution_pending`，执行成功后进入 `executed`。
- 拒绝后 proposal 进入 `rejected`，并且不产生业务写入。
- 修改 proposal 时，旧 proposal 进入 `revised` 或 `superseded`，新 proposal 重新进入 `pending`。
- 同一个 confirmed proposal 重复确认不得重复创建 event / task。
- 多 proposal 并存时，用户只说“可以”不得被系统猜测为任意一个 proposal。
- 文本回复不能出现“点按钮”“点击这里”等与纯文本协议冲突的主流程话术。
- 用户补充缺失槽位时，系统必须复用最近相关请求中的主题、地点、时间上下文。
- 单 pending proposal 下，用户只补充时间、地点、标题等槽位时，应优先视为 revise 当前 proposal，而不是新建无关 proposal 或追问已知信息。
- 用户对已有 pending proposal 说“创建独立日程”“就按这个生成”等执行导向话术时，系统不得复制生成同义 proposal；应引导确认已有 proposal。
- LLM 误判不得突破产品协议：带明确时间和地点的提醒型请求仍应按日程 / 提醒事件 proposal 处理。

## 三、测试数据基线

建议在每轮浏览器验收前准备以下数据：

- 用户常用地点：
  - 家：测试家庭地址
  - 学校：测试学校地址
  - 驾校：测试驾校地址
- 明天日程：
  - 15:00 - 16:00 图书馆自习
  - 19:00 - 20:00 晚间复习
- 任务：
  - 毕设论文，优先级高，deadline 为 3 天后，未排程
  - 英语复习，优先级中，未排程
  - 高数复习，deadline 为 7 天后，未排程，用于同类任务歧义测试
- 记忆文件：
  - `places.md` 包含学校、家两个已确认别名
  - `preferences.md` 不包含本轮测试新增偏好
  - `habits.md` 可为空或包含默认起床 / 睡前时间
- Proposal 状态样本：
  - 至少能构造 pending、executed、rejected、superseded、expired、execution_failed 六类 proposal。
  - 至少能构造两个并存 pending proposal，且展示协议标签 `P1`、`P2`。
- 并发与恢复样本：
  - 可打开两个浏览器窗口使用同一测试用户。
  - 可临时停止后端、断开网络、或切换 AI provider mock 状态。

若某用例需要特殊前置数据，应按该用例单独设置，执行后清理。

## 四、P0 阻断级测试

### BAI-P0-001 明确日程创建必须先提案

- 前置条件：明天下午 15:00 无冲突或冲突已清理。
- 浏览器输入：`明天下午三点去学校上政治课`
- 预期结果：
  - 当前对话区生成一次性日程 proposal，语义为 `event_creation`。
  - 文本包含结论、原因、方案、建议、可回复示例。
  - 至少出现 `方案 A`，包含开始时间、地点、标题。
  - 当前待确认事项区出现 1 条 pending proposal。
  - 刷新日程页后，不应出现“政治课”事件。

### BAI-P0-002 单 proposal 自然语言确认执行

- 前置条件：已完成 BAI-P0-001，且只有一个 pending proposal。
- 浏览器输入：`可以`
- 预期结果：
  - 系统将该回复映射为确认当前 proposal。
  - proposal 状态从 `pending` 进入 `execution_pending`，随后进入 `executed`。
  - 日程页出现“政治课”，时间为明天下午 15:00，地点为学校。
  - 当前待确认事项区不再显示该 proposal 为待确认。
  - 再次刷新页面后，事件仍存在且没有重复。

### BAI-P0-003 重复确认幂等

- 前置条件：BAI-P0-002 已执行成功。
- 浏览器输入：`可以`
- 预期结果：
  - 系统不得再次创建“政治课”事件。
  - 对话区应返回已执行或当前状态说明。
  - 日程页仅有 1 条对应事件。
  - proposal 执行回执保持同一个业务结果。

### BAI-P0-004 模糊任务请求不得直接拆日程

- 前置条件：无同名 pending proposal。
- 浏览器输入：`帮我安排一下复习`
- 预期结果：
  - 系统判断为长期任务或任务排程请求。
  - 若信息不足，应先澄清科目、deadline、可用时段或生成低风险 task proposal。
  - 不得直接创建多个复习日程块。
  - 若生成 proposal，必须在待确认事项区显示 pending 状态。

### BAI-P0-005 任务 / 日程类型澄清

- 前置条件：先输入 `明天安排一下复习`，系统生成一次性日程倾向 proposal。
- 浏览器输入：`这个是任务，不是单次日程`
- 预期结果：
  - 系统承认类型修正，不应继续按单次日程处理。
  - 旧 proposal 进入 `revised` 或 `superseded`。
  - 新 proposal 类型应偏向 `task_creation` 或 `task_schedule_plan`。
  - 未确认前不得创建任务或日程块。

### BAI-P0-006 自然语言修改 proposal

- 前置条件：存在 1 个 pending event proposal，开始时间为 15:00。
- 浏览器输入：`改成4点开始`
- 预期结果：
  - 系统映射为 `revise(proposal_id, patch=start_time:16:00)`。
  - 旧 proposal 进入 `revised` 或 `superseded`。
  - 新 proposal 重新进入 `pending`，方案时间变为 16:00。
  - 日程页仍无实际事件写入。

### BAI-P0-007 拒绝 proposal

- 前置条件：存在 1 个 pending proposal。
- 浏览器输入：`先不要安排`
- 预期结果：
  - proposal 状态进入 `rejected`。
  - 待确认事项区移除或显示已拒绝。
  - 不创建、不修改、不删除任务或日程。
  - 系统回复应说明已暂不安排，而不是继续追问确认。

### BAI-P0-008 多 proposal 下“可以”必须澄清

- 前置条件：当前同时存在 `P1 小组会调整`、`P2 复习顺延` 两个 pending proposal。
- 浏览器输入：`可以`
- 预期结果：
  - 系统不得猜测确认 P1 或 P2。
  - 对话区必须询问用户明确 `P1` 还是 `P2`。
  - 两个 proposal 状态均保持 `pending`。
  - 业务数据无任何写入。

### BAI-P0-009 多 proposal 带标识确认

- 前置条件：当前同时存在 `P1`、`P2` 两个 pending proposal。
- 浏览器输入：`P1 按方案A安排`
- 预期结果：
  - 仅 P1 被确认并执行。
  - P2 继续保持 `pending`。
  - 实际业务写入只对应 P1。
  - 待确认事项区仍展示 P2 的短标识和摘要。

### BAI-P0-010 冲突日程必须给多方案

- 前置条件：明天 15:00 - 16:00 已有“图书馆自习”。
- 浏览器输入：`明天下午三点去学校和同学见面`
- 预期结果：
  - 系统识别时间冲突。
  - 生成 proposal，而不是直接覆盖或并排创建。
  - 至少给出两个方案，例如保留原时间但提示冲突、改到空档、缩短或顺延。
  - 推荐方案必须解释原因。
  - 未确认前不得改动“图书馆自习”。

### BAI-P0-011 批量调整必须拆成可确认动作

- 前置条件：明天存在 3 条日程。
- 浏览器输入：`把明天所有日程都推迟一天`
- 预期结果：
  - 系统生成 `reschedule_plan` proposal。
  - proposal 文本列出受影响日程。
  - 如果每条日程目标独立，应拆成多个子 proposal 或在 proposal 内明确多个 action 的执行快照。
  - 未确认前，日程页无变化。
  - 确认后，每条受影响日程只调整一次。

### BAI-P0-012 过大批量调整必须防失控

- 前置条件：目标日期存在超过 8 条日程或任务切片。
- 浏览器输入：`把明天所有安排都取消`
- 预期结果：
  - 系统不得静默取消全部事项。
  - 应列出影响范围并要求更明确确认，或提示批量范围过大需要拆分。
  - 未确认前所有日程和任务状态不变。

### BAI-P0-013 多轮日程槽位补全必须继承上下文

- 前置条件：干净会话，当前无 pending proposal 或先清空。
- 浏览器输入序列：
  1. `3个小时后提醒我去学校`
  2. `下午1点开始，晚上10点结束`
  3. `创建独立日程`
- 预期结果：
  - 第 1 轮应识别为 `event_creation`，标题或主题为“去学校”，地点可解析为学校，生成 pending proposal；不得误生成为“个小时后去学校”的 task proposal。
  - 第 2 轮应继承“去学校”上下文，并将 pending proposal revise 为 13:00 - 22:00；旧 proposal 进入 `superseded` 或 `revised`，新 proposal 保持 `pending`。
  - 第 3 轮不得再次询问标题、开始时间、结束时间，也不得复制生成同义 P2；应提示已有待确认独立日程方案，并引导用户回复 `确认 P1 方案A` 或继续修改。
  - 全流程未确认前，日程页和 events 表仍无“去学校”事件落库。
  - 刷新页面后，待确认事项区仍只展示最新 pending proposal，标签和摘要稳定。

### BAI-P0-014 单 pending proposal 下纯时间补充必须走 revise

- 前置条件：存在 1 个 pending event proposal，标题为“去学校”，时间为 15:00 - 16:00。
- 浏览器输入：`下午1点开始，晚上10点结束`
- 预期结果：
  - 系统将该回复理解为对当前 proposal 的时间补充 / 修改。
  - 新 proposal 时间为 13:00 - 22:00，旧 proposal 进入 `superseded` 或 `revised`。
  - 不应生成“改期日程请求，需要补充具体日程”的澄清。
  - 不应创建第二个语义重复的 event_creation proposal。

### BAI-P0-015 已有 pending proposal 时执行导向话术不得复制 proposal

- 前置条件：存在 1 个 pending event proposal，摘要为“建议创建日程‘去学校’”。
- 浏览器输入：`创建独立日程`
- 预期结果：
  - 系统应说明已有待确认独立日程方案，并给出确认文本示例。
  - 不应创建新的同义 proposal。
  - 不应追问已知的标题、开始时间、结束时间或地点。
  - 未确认前不写入日程。

### BAI-P0-016 带时间和地点的提醒不得误判为普通任务

- 前置条件：干净会话，AI provider 可正常调用。
- 浏览器输入：`3个小时后提醒我去学校`
- 预期结果：
  - 系统生成 `event_creation` proposal 或提醒型 event proposal。
  - 标题 / 主题保留“去学校”，不得变成“个小时后去学校”。
  - 开始时间应按当前时间 + 3 小时解析，若结束时间缺失，应说明默认时长或提醒策略。
  - 未确认前不创建 event / task。

### BAI-P0-017 连续发送与加载状态不得吞消息或重复提交

- 前置条件：干净会话，选择一条会触发较慢 AI 调用的输入。
- 浏览器操作：
  1. 输入 `3个小时后提醒我去学校` 并发送。
  2. 在发送中连续点击发送按钮或快速输入下一句。
  3. 待第一轮完成后输入 `下午1点开始，晚上10点结束`。
- 预期结果：
  - 发送期间按钮应禁用或明确显示加载状态。
  - 快速重复点击不得生成重复用户消息或重复 proposal。
  - 发送锁释放后，第二句应可正常发送并进入 revise 逻辑。
  - 若用户在发送中输入内容，前端不得静默丢失用户可见草稿；至少应保持可重发状态。

## 五、日程、任务与排程场景

### BAI-P1-001 不完整日程应澄清

- 浏览器输入：`我要去学校和同学见面`
- 预期结果：
  - 系统识别地点和主题，但发现缺少日期 / 时间。
  - 对话区提出明确澄清问题。
  - 不生成可执行 event，不创建日程。

### BAI-P1-002 带自然语言时间的日程

- 浏览器输入：`后天上午十点到十一点在培训室培训`
- 预期结果：
  - 生成 event proposal，标题类似“培训”。
  - 方案时间解析为后天 10:00 - 11:00。
  - 地点为培训室。
  - 需用户确认后才写入。

### BAI-P1-003 默认时长推断

- 浏览器输入：`明天下午三点去学校开组会`
- 预期结果：
  - 若用户未给结束时间，系统可给出默认时长方案。
  - 文本必须说明默认时长依据，例如按 1 小时暂定。
  - 用户可通过 `结束时间缩短半小时` 或 `开到5点` 修改。

### BAI-P1-004 任务创建

- 浏览器输入：`提醒我整理毕设论文`
- 预期结果：
  - 系统生成 task proposal 或先询问 deadline / 优先级。
  - 不应直接创建日程块。
  - 若用户确认，任务页出现“整理毕设论文”。

### BAI-P1-005 任务排程

- 前置条件：存在未排程任务“整理毕设论文”。
- 浏览器输入：`把整理毕设论文安排到未来三天下午3点到5点`
- 预期结果：
  - 生成 `task_schedule_plan` proposal。
  - 方案包含三天各 15:00 - 17:00 的执行切片。
  - 执行切片应与父任务关联。
  - 未确认前不创建日程块。
  - 确认后创建 3 个普通日程块，不引入复杂 recurrence rule。

### BAI-P1-006 有限期重复任务完成判定

- 前置条件：已确认一个“三天论文写作”父任务及 3 个执行切片，且 3 个切片均完成。
- 浏览器输入：`论文这三天的写作都完成了`
- 预期结果：
  - 系统可生成完成确认 proposal 或在睡前批量确认中处理。
  - 对可量化任务，所有执行块终态后父任务可进入 done。
  - 对结果型任务，应询问最终结果是否完成。

### BAI-P1-007 取消重复任务单个切片

- 前置条件：存在未来三天复习切片。
- 浏览器输入：`明天那个复习块不做了`
- 预期结果：
  - 系统应询问或生成 proposal，区分“取消但待补排”和“本次跳过不补排”。
  - 不应直接把父任务标记完成。

### BAI-P1-008 查询进展不应写入

- 浏览器输入：`现在毕设论文进展怎么样，接下来怎么安排`
- 预期结果：
  - 系统读取任务和日程上下文，给出进展摘要和建议。
  - 若建议新排程，应生成 proposal。
  - 单纯查询不得改变任务、日程、proposal 状态。

### BAI-P1-009 多轮时间补全后再补地点

- 前置条件：存在一个 pending event proposal，标题已定为“去学校”，开始时间已定。
- 浏览器输入序列：
  1. `下午1点开始`
  2. `晚上10点结束`
  3. `地点改成图书馆`
- 预期结果：
  - 第 1、2 轮应在同一个 proposal 上逐步补全时间槽位。
  - 第 3 轮应改写地点，不应新建 proposal。
  - 若地点和现有标题冲突，应在 proposal 文本中反映冲突或给出更稳妥的解释。

### BAI-P1-010 先改标题再改时间

- 前置条件：存在 1 个 pending event proposal，标题为“去学校”。
- 浏览器输入序列：
  1. `标题改成和同学见面`
  2. `改到下午4点`
- 预期结果：
  - 标题修改和时间修改都应落在同一 revision 链上。
  - 旧 proposal 进入 `superseded`，新 proposal 保持 `pending`。
  - 变更结果必须可在待确认事项区读到。

### BAI-P1-011 只给结束时间的部分修正

- 前置条件：存在 1 个 pending event proposal，开始时间为 15:00，结束时间为 16:00。
- 浏览器输入：`结束时间缩短半小时`
- 预期结果：
  - 系统只调整 end_time，不应重新问开始时间。
  - 结果应体现为 15:00 - 15:30 或等价表达。
  - 不应丢失原 proposal 的标题、地点和上下文。

### BAI-P1-012 跨午夜时间段解析

- 浏览器输入：`今晚11点到凌晨1点在学校值班`
- 预期结果：
  - 系统应正确识别跨午夜时间段，而不是把结束时间误判到同一天更早时刻。
  - 生成 event proposal 后，开始与结束时间应明确跨日。

### BAI-P1-013 相对日期与绝对日期混用

- 浏览器输入：`下周三上午9点到11点去学校，5月15日如果冲突就改到下午`

  - 系统至少应识别主时间段，并对补充条件作出提示或澄清。

### BAI-P1-014 同句包含多个日程目标

  - 可以拆成多个 proposal，或者先澄清要先处理哪一个。
  - 未确认前不得自动创建多个事件。

### BAI-P1-015 任务与日程混合句应拆分语义

- 浏览器输入：`明天先去学校开会，顺便提醒我整理毕设论文`

  - 系统不得把任务提醒吞进日程标题。
  - 可生成一个 event proposal + 一个 task proposal，或先澄清主次。

### BAI-P1-016 模糊“去学校”需要结合上下文

### BAI-P1-109 多地点同名歧义

- 预期结果：
  - 发送期间输入框或发送按钮有明确加载状态。
  - 不允许连续快速点击造成重复消息提交。
  - 失败时能恢复可输入状态并显示错误。

### BAI-P1-406 WebSocket 状态同步

- 前置条件：打开助手页面，同时通过另一个浏览器窗口确认一个 proposal。
- 浏览器操作：观察第一个窗口。
- 预期结果：
  - 第一个窗口的待确认事项区自动更新或在刷新后准确更新。
  - 不应继续显示已 executed 的 proposal 为可确认。

### BAI-P1-407 会话切换不得串上下文

- 前置条件：会话 A 中存在“去学校” pending proposal，会话 B 为空。
- 浏览器操作：
  1. 在会话 A 输入 `改到下午4点`。
  2. 切换到会话 B 输入 `可以`。
- 预期结果：
  - 会话 A 的 proposal 可被 revise。
  - 会话 B 不得确认会话 A 的 proposal，除非全局 pending proposal 区有明确标签并用户显式指定。
  - UI 应清楚显示当前会话和当前待确认事项范围。

### BAI-P1-408 长对话滚动与最新消息可见

- 前置条件：当前会话已有 30 条以上消息，含多个长 proposal 文本。
- 浏览器输入：`明天下午三点去学校上课`
- 预期结果：
  - 最新用户消息和助手回复可见或自动滚动到合理位置。
  - 输入框不被历史内容遮挡。
  - 待确认事项区仍可访问，不因长消息撑破布局。

### BAI-P1-409 Markdown 与特殊字符安全

- 浏览器输入：``明天3点去学校，标题叫<script>alert(1)</script>``
- 预期结果：
  - UI 不执行脚本。
  - 标题展示应被转义或清洗。
  - 若生成 proposal，payload 不应包含可执行 HTML。

### BAI-P1-410 标签稳定性跨刷新和 revision

- 前置条件：存在 P1，用户随后修改生成新版 proposal。
- 浏览器操作：刷新页面。
- 预期结果：
  - 旧 proposal 不再作为 pending P1 展示。
  - 新 pending proposal 的协议标签稳定，前端显示与后端 payload 中 `protocol_label` 一致。
  - 文本确认示例使用刷新后的真实标签。

### BAI-P1-411 多 pending proposal 区域排序

- 前置条件：存在 5 个 pending proposal，类型混合为日程、任务、记忆候选转 proposal、出发建议。
- 浏览器操作：打开助手页面。
- 预期结果：
  - 待确认事项区排序稳定，可按创建时间或优先级解释。
  - 每条 proposal 的类型、状态、摘要可区分。
  - 不因超过 5 条而破坏布局；若折叠，应有可恢复查看方式。

## 十、异常、失败与回退场景

### BAI-P1-501 Provider 失败 fallback

- 前置条件：测试环境可临时使主模型调用失败，并配置 fallback。
- 浏览器输入：`明天下午三点去学校上政治课`
- 预期结果：
  - 系统仍能给出结构化 proposal 或明确说明临时不可用。
  - 不出现空白回复、无限加载或前端崩溃。
  - 若 fallback 成功，proposal 规则仍保持一致。

### BAI-P1-502 Provider 全部失败

- 前置条件：测试环境使所有 AI provider 不可用。
- 浏览器输入：`帮我安排一下复习`
- 预期结果：
  - UI 显示可理解的失败提示。
  - 不创建任何任务、日程、proposal 执行动作。
  - 输入框恢复可用，允许用户稍后重试。

### BAI-P1-503 执行失败进入 retry

- 前置条件：构造一个确认后执行会失败的 proposal。
- 浏览器输入：`按方案A安排`
- 预期结果：
  - proposal 进入 `execution_failed`。
  - UI 显示失败原因和可重试入口或可回复方式。
  - 再次确认不应重复执行；应走 retry 语义。

### BAI-P1-504 expired proposal 不可确认

- 前置条件：存在已过期 proposal。
- 浏览器输入：`按方案A安排`
- 预期结果：
  - 系统拒绝执行已过期 proposal。
  - 对话区说明该方案已过期，并可生成新的 proposal。
  - 不写入业务数据。

### BAI-P1-505 superseded proposal 不可确认

- 前置条件：P1 已被 P2 替代。
- 浏览器输入：`P1 按方案A安排`
- 预期结果：
  - 系统提示 P1 已被替代。
  - 不执行 P1。
  - 引导用户确认 P2 或重新生成方案。

### BAI-P1-506 无效方案编号

- 前置条件：存在 P1，只有方案 A 和 B。
- 浏览器输入：`P1 按方案C安排`
- 预期结果：
  - 系统提示方案 C 不存在。
  - P1 保持 pending。
  - 不执行任何业务写入。

### BAI-P1-507 网络中断恢复

- 浏览器操作：发送请求过程中断网或停止后端，再恢复。
- 预期结果：
  - 前端展示失败或重连状态。
  - 恢复后可继续发送消息。
  - 不因重连重复执行上一次确认。

### BAI-P1-508 后端重启后 pending proposal 可继续确认

- 前置条件：存在 1 个 pending proposal，前端页面保持打开。
- 浏览器操作：
  1. 重启后端。
  2. 刷新或等待 WebSocket 重连。
  3. 输入 `确认 P1 方案A`。
- 预期结果：
  - pending proposal 从数据库恢复并可继续确认。
  - 不应因内存 active target 丢失而提示“没有待确认方案”。
  - 执行后状态进入 executed，业务写入一次。

### BAI-P1-509 数据库写入失败不应显示成功

- 前置条件：构造 event 写入失败，例如数据库只读或约束冲突。
- 浏览器输入：`确认 P1 方案A`
- 预期结果：
  - UI 显示执行失败，不应显示“已创建”。
  - proposal 状态进入 `execution_failed`。
  - 业务表中不存在半写入脏数据，或有明确回滚策略。

### BAI-P1-510 AI 返回格式异常

- 前置条件：mock AI provider 返回非 JSON、空文本、超长文本或与协议冲突的“我已经创建了”。
- 浏览器输入：`明天下午三点去学校上政治课`
- 预期结果：
  - 系统应通过后端协议层兜底，仍保持 proposal-first。
  - 不得因为 AI 文本说“已创建”就直接落库。
  - 若无法解析，应给出可理解失败提示。

### BAI-P1-511 慢响应超时与重试

- 前置条件：mock AI provider 延迟超过前端默认等待时间。
- 浏览器输入：`帮我把毕设论文排到未来三天`
- 预期结果：
  - 前端不应无限 loading。
  - 若请求超时，系统提示稍后重试，输入框恢复。
  - 后端晚到结果不得在用户重试后造成重复 proposal，除非有明确去重。

## 十一、旧行为回归防线

### BAI-P0-101 不得硬分句误拆

- 浏览器输入：`中午12点我要去驾校接李婷`
- 预期结果：
  - 系统应理解为一个完整事务。
  - 标题不应被拆成“中午12点我要去驾校”和“接李婷”两个不相关部分。
  - 如果生成 proposal，应包含合理标题、时间、地点和目的。

### BAI-P0-102 不得绕过 proposal 直接写入

- 浏览器输入：`明天上午9点帮我创建一个去学校开会的日程`
- 预期结果：
  - 即使用户说“创建”，系统仍先生成 proposal。
  - 未确认前日程页无新增事件。

### BAI-P0-103 普通建议不应触发旧 workflow 文案

- 浏览器输入：`我明天有点忙，帮我看看怎么安排比较合理`
- 预期结果：
  - 系统应给出上下文建议或生成 proposal。
  - 不应出现旧 workflow、节点名、工具链调试文案。
  - 不应回复无法理解简单事务需求。

### BAI-P0-104 未知请求应澄清而不是乱执行

- 浏览器输入：`帮我处理一下那个事情`
- 预期结果：
  - 系统要求用户明确“那个事情”指什么。
  - 不创建任何任务或日程。
  - 不生成无目标 proposal。

### BAI-P0-105 不得把补充回答当成全新无关任务

- 前置条件：上一轮助手询问日程缺失信息，例如缺少结束时间。
- 浏览器输入：`晚上10点结束`
- 预期结果：
  - 系统应尝试关联上一轮日程请求。
  - 如果无法关联，应说明需要重新确认原请求，而不是生成“晚上10点结束”任务。

### BAI-P0-106 不得在无确认时写入长期记忆

- 浏览器输入：`我今天在图书馆，下午去学校`
- 预期结果：
  - 系统可把“图书馆”作为本轮上下文。
  - 不得直接写入 `places.md` 或偏好文件。

### BAI-P0-107 不得把中文相对时间解析为持续时长

- 浏览器输入：`3个小时后提醒我去学校`
- 预期结果：
  - `3个小时后` 应解析为开始时间相对当前时间 + 3 小时。
  - 不应解释为持续 3 小时，除非用户说“持续3小时”或“预计3小时”。

### BAI-P0-108 不得确认已被替代的旧 proposal

- 前置条件：P1 已因修改进入 `superseded`，P2 为最新 pending proposal。
- 浏览器输入：`P1 按方案A安排`
- 预期结果：
  - 系统提示 P1 已被替代。
  - 不执行 P1，也不写入业务数据。
  - 引导用户确认 P2 或重新生成方案。

### BAI-P0-109 不得把“可以”绑定到 active target 覆盖多 proposal 歧义

- 前置条件：当前 active target 指向 P1，但待确认事项区同时存在 P1、P2。
- 浏览器输入：`可以`
- 预期结果：
  - 系统必须澄清 P1 还是 P2。
  - 不得因为 active target 自动确认 P1。

### BAI-P0-110 不得因刷新重新编号导致文本确认错配

- 前置条件：存在多个 pending proposal，刷新页面后用户按 UI 显示的 P1 确认。
- 浏览器输入：`P1 按方案A安排`
- 预期结果：
  - 后端执行的必须是 UI 上显示的 P1。
  - protocol label 必须持久化，前端不得仅按本地排序临时编号。

## 十二、建议自动化优先级

### P0 必须自动化

- 明确日程创建 proposal
- 单 proposal 确认执行
- 重复确认幂等
- 多轮上下文继承与 slot 补全
- 单 pending proposal 的 revise 继承
- 模糊任务不直接拆日程
- 自然语言 revise
- proposal reject
- 多 proposal 歧义澄清
- 已存在 pending proposal 时的“创建独立日程”防复制
- 带时间的提醒型请求不得误判为普通任务
- 冲突日程多方案
- 不得绕过 proposal 直接写入
- 硬分句回归用例

### P1 建议自动化

- 任务排程三天切片
- 跨午夜时间段解析
- 单纯结束时间 / 标题 / 地点补充
- 出发提醒文本协议
- deadline 风险 signal
- signal / proposal 去重
- 晨间汇报固定模板
- 睡前批量完成
- 记忆候选确认 / 拒绝
- 多地点同名歧义
- 标签稳定性跨刷新与 revision
- 会话切换与并发同步
- 移动端布局
- Provider 失败 fallback
- 后端重启后 pending proposal 恢复
- 失败写入和 AI 异常兜底

### P2 可人工验收

- 复杂记忆冲突语义
- 同句多个独立目标拆分质量
- 多轮长对话的自然度和修正连贯性
- 长期偏好候选质量
- 文本自然度和推荐理由质量
- 多轮协商中的推荐策略是否符合用户习惯
- 不同天气、通勤估算供应商下的出发建议质量
- 特殊字符清洗和标题展示质量

## 十三、验收退出标准

本轮浏览器级测试可视为通过时，应同时满足：

1. 所有 P0 用例通过。
2. P1 用例通过率不低于 90%，未通过项必须有缺陷单或任务书跟踪项。
3. 任意写操作在未确认前均无数据库或长期记忆落库。
4. proposal 幂等、reject、revise、expired、superseded 均有浏览器级覆盖。
5. 主动跟进不会重复刷屏，且每条主动消息都有来源、理由和回复方式。
6. 浏览器刷新、移动端视口、网络失败恢复不破坏 pending proposal 状态。
7. 不出现旧 workflow 行为、调试文案、弱规则误拆或无确认直接执行。
